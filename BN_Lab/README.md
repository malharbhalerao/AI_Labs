## Answers to Questions

### Part I & II
**Question 1:** 
The chain-rule decomposition is useful because it breaks down the complex joint probability of an entire sentence ($P(X_{1}, ..., X_{T})$) into a sequence of conditional probabilities ($P(X_{t}\vert{}X_{1...t-1})$). This allows the model to generate text sequentially, predicting one word at a time based only on the preceding context.

**Question 2:** 
The first-order Markov model makes the independence assumption that a word relies *only* on the immediately preceding word. In probability notation: $P(X_{t} \vert{} X_{1}, X_{2}, ..., X_{t-1}) \approx P(X_{t} \vert{} X_{t-1})$.

### Part IV
**Question 3:** 
See Deliverable 3 above for the computed distributions. Zero-probability transitions include $P(mat\vert{}sat) = 0$ and $P(ran\vert{}the) = 0$.

### Part VI
**Question 4:** 
Transition counts are stored in a nested dictionary `self.counts[current_word][next_word]`.

**Question 5:** 
The conditional probability $P(X_{t}\vert{}X_{t-1})$ is computed during the `train()` phase by dividing the specific transition count by the total occurrences of the current word: `count / sum(transitions.values())`.

**Question 6:** 
The program supports both. The greedy method uses `max()` to deterministically pick the highest probability word. The sampling method uses `random.choices(weights=probabilities)` to pick a word probabilistically. Sampling allows for generation variation; greedy generation will always output the exact same sentence given the same starting word.

**Question 7:** 
If it encounters a word with no observed transitions, the dictionary lookup fails, or the context returns no options, ending the sequence abruptly. The implementation handles this by defaulting to `<END>` if an unknown state is reached.

### Part VII
**Question 8:** 
If a total is 0.87, it means the probability distribution does not sum to 1. This indicates a flaw in the implementation—likely floating-point precision errors during division, or the omission of certain transitions (e.g., forgetting to count the `<END>` token) when computing the denominator.

### Part VIII
**Question 9:** 
The most probable predictions generated by the model are restricted strictly to the training data. For example, $\arg\max_{w} P(w\vert{}the)$ might be "cat" or "dog" based on this tiny dataset, whereas human linguistic expectations would include a massive variety of nouns. This demonstrates that a probability model's "worldview" is entirely bound by its training corpus, unlike human cognition which draws on semantic understanding and vast real-world exposure.

### Part X
**Question 10:** 
Mode B (Sampling) produces significantly more variation. Greedy generation gets trapped in the most probable path, always outputting "the cat sat on the mat" when initialized. Sampling allows the model to randomly take less probable, but valid, branches (e.g., generating "the dog ran to the park"), leading to diverse text generation.

### Part XI
**Question 11:** 
1. **Graph Structure:** Edges point from both $X_{t-2}$ and $X_{t-1}$ to $X_{t}$.
2. **CPT:** The conditional probability table is indexed by pairs of words (tuples) rather than single words.
3. **Context:** Two prior words are used to predict the next token instead of one.
4. **Data:** It requires significantly more training data to avoid sparsity, as the number of possible two-word combinations is the square of the vocabulary size.

### Part XIII
**Question 12:** 
Increasing context improves prediction because it reduces ambiguity (e.g., knowing "sat on" gives a much better clue for "the" or "mat" than just knowing "on"). However, it makes estimation harder from limited data because the state space expands exponentially. This creates a massive CPT filled mostly with zeroes (unseen contexts), meaning the model will frequently encounter sequences it doesn't know how to complete.

### Part XV
**Question 13:** 
Approach B is preferable because it forces the developer to strictly define the mathematical and behavioral constraints of the model (estimating $P(X_{t}\vert{}X_{t-1})$ via counts and sampling). Prompting for just a "Python language model" might cause the LLM to hallucinate complex ML libraries, import PyTorch, or generate an unstructured markov chain. Approach B ensures the LLM's output can be verified against known probabilistic invariants, clearly separating the conceptual model from the code implementation.

### Part XVI
**Question 14:** 
Framing the language model as a Bayesian Network provides:
1. **A representation of dependencies:** Visualizing nodes ($X_{1} \rightarrow X_{2}$) makes the Markov assumptions immediately obvious.
2. **A principled method for generation:** It dictates that text generation is mathematically equivalent to ancestral sampling from a directed acyclic graph.
3. **A way to understand the effect of increasing context:** Moving to a second-order model visually adds edges to the graph ($X_{t-2} \rightarrow X_{t}$), clearly demonstrating how the conditional parameter space grows and requires more data to estimate accurately.

## Deliverable 7: Reflection on LLM Usage

During the implementation phase, the LLM was utilized by strictly outlining the probabilistic constraints (Approach B) rather than asking for open-ended code generation. 

**Inspection and Correction Example:**
Initially, when writing the second-order model, the LLM-generated code attempted to index the Conditional Probability Table using a sliding list window:
`self.counts[sentence[i-2:i]][next_word] += 1`
Upon inspection, I recognized that lists cannot be used as dictionary keys in Python because they are mutable objects. I corrected the implementation to explicitly extract a tuple before using it as a key: 
`context = (sentence[i-2], sentence[i-1])`
`self.counts[context][next_word] += 1`

Validating the code through the `test_normalization` function was critical. It ensured that regardless of how the loops were structured, the fundamental Bayesian requirement—that the conditional probability table sums to 1.0 across all outcomes for a given context—was mathematically satisfied.
